# 维护与发布

## 源码与数据

| 路径 | 用途 |
| --- | --- |
| `src/` | PLC 模型和通信驱动、MQTT、接入助手、本地诊断和 HTTP 服务 |
| `web/` | 用户界面、品牌接入指南、诊断报告字段和浏览器汇总 |
| `tools/`、`tests/` | 一键命令的实现、独立协议对测、回归和打包 |
| `docs/` | 使用手册、验证记录和维护流程 |
| `project.json` | 默认端口和模拟参数 |
| `data/`、`logs/`、`exports/` | 各安装自己的项目、协议记录、本地日志和手动导出 |
| `runtime/`、`node_modules/`、`dist/` | 运行时、依赖和发布产物 |

在对应的实现旁注释模型边界、兼容字段和判定依据。用户界面保留操作说明、单位、状态与故障处理。公开源码与离线包均按发布清单排除用户数据。

## 版本与更新

软件版本取自 `package.json`，健康接口、诊断报告和打包工具共用这个值。锁文件保存相同版本。兼容修复增加末位，兼容新功能增加中位，不兼容修改增加首位。诊断报告的格式版本独立于软件版本，当前为 `industrial-bench-diagnostics/1`。规则见[语义化版本](https://semver.org/lang/zh-CN/)。

升级已有安装时，先停止老版本，备份原目录。把新版完整解压到新目录，复制原 `data/` 以保留项目、按钮、历史和诊断，再按需迁移 `project.json` 中自行修改的端口。关闭旧服务后启动新版并做自测。回退时关闭新版，使用老版本与升级前的备份。每个用户自行决定何时下载新版本。

## 发布一个版本

1. 在 Windows x64 的干净工作区准备 Node.js 24+ 和 Python 3.10+。运行 `npm ci --ignore-scripts`、`npm test`。需要验证厂商协议时运行 `tools/verify_s7.py`，界面验收使用 `tools/verify_ui.py`。两套额外验证依赖见脚本开头。
2. 用 `npm version minor --no-git-tag-version` 或 `npm version patch --no-git-tag-version` 同步软件和锁文件版本。在 `CHANGELOG.md` 写日期、变化和必要的迁移步骤。
3. 从 Node.js 官方发行目录取 `package.json` 的 `portableRuntime.version` 对应的 Windows x64 运行时，将 node.exe 和随包 LICENSE 分别放入 `runtime/node.exe`、`runtime/LICENSE-node.txt`。升级运行时时，用官方 SHA-256 清单核实并更新 `portableRuntime.windowsX64Sha256`。[Node.js 发布目录](https://nodejs.org/dist/)
4. 暂存本次源码，执行 `python tools/package_release.py`。它按锁文件安装干净的依赖，核对版本、官方运行时摘要、更新记录和 Git 发布清单，在 `dist/` 生成 ZIP 和 SHA-256。已准备干净的依赖时，可用 `--dependencies 路径` 指向该 node_modules 目录。
5. 在新的中文目录解压 ZIP，运行启动、状态、自测、导出诊断和停止。再提交源码，给同一个提交打 `v主.次.修订` 标签。发布 GitHub Release，附上 ZIP 与同名 `.sha256` 文件。可以用 PowerShell 的 `Get-FileHash -Algorithm SHA256` 核对下载文件。[GitHub Release 操作说明](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)

## 诊断约定

每个安装生成独立的随机编号，每次服务启动产生运行编号。每条事件带顺序号、时间、配置中的设备品牌、实际选用的驱动和所属通信环节。等待外部软件启动与已发现的错误分别计数。重复的轮询故障只记录状态变化，恢复时再记一条。试连按试用的配置归类，即使它尚未保存。

字段白名单在 `web/report-format.js`。新增诊断同时补充中文名称、原因和测试。保留按安装、运行和序号去重的规则。诊断仅在回环地址和本机文件间流转。厂家工程、MQTT 原文、系统用户名、设备账号与实际地址保留在各用户自己的运行环境中。
